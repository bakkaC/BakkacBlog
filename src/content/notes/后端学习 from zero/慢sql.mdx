## N+1 问题

典型代码：

```typescript
const books = Book.getAll()
books.forEach(book => {
  const author = Author.findById(book.authorId)
  console.log(`${book.name} was written by ${author.name}.`)
})
```

它会产生类似这样的查询：

```sql
select name, authorId from books;

select name from authors where authors.id = ${book_1.authorId};
select name from authors where authors.id = ${book_2.authorId};
select name from authors where authors.id = ${book_3.authorId};
...
```

如果有 100 本书，就会运行 101 次查询。

优化方向是预加载，用一次查询加载所有书籍及其作者：

```sql
select books.name as name,
       authors.name as authorName
from books
join authors on books.authorId = authors.id;
```

## JOIN、子查询、去重

| SQL 写法 / 特征 | 为什么容易慢 | 常见问题 | 优化方向 |
| --- | --- | --- | --- |
| 多表 JOIN | 中间结果膨胀 | 性能指数级下降 | 控制 JOIN 数量 |
| JOIN 字段类型不一致 | 无法高效匹配 | 隐式转换 | 类型统一 |
| 子查询 | 可能物化临时表 | 中间结果大 | 改 JOIN |
| 相关子查询 | 外层逐行执行 | N+1 问题 | 改 JOIN |
| `UNION` | 自动去重排序 | 多一层排序 | 用 `UNION ALL` |
| 大宽表 JOIN | IO 放大 | 行数据太大 | 拆表 / 冗余字段 |

## 排序、聚合、表达式

| SQL 写法 / 特征 | 为什么容易慢 | 常见问题 | 优化方向 |
| --- | --- | --- | --- |
| `ORDER BY` 无索引 | filesort | 全量排序 | 建排序索引 |
| `GROUP BY` 无索引 | 临时表 + 排序 | 聚合慢 | 联合索引 |
| `DISTINCT` | 排序 / 哈希去重 | 大开销 | 减少数据量 |
| `HAVING` 过滤 | 先聚合再过滤 | 多余计算 | 改 `WHERE` |
| `ORDER BY + LIMIT` | 可能全量排序 | TOP N 慢 | 索引优化 |
| 复杂表达式计算 | 每行 CPU 计算 | CPU 高 | 预计算字段 |

聚合查询不是把每一行原样查出来，而是把多行数据汇总成一个结果。

常见聚合函数：

```sql
count(*)
sum(amount)
avg(score)
max(price)
min(price)
```

聚合查询慢的核心原因是它往往必须扫描大量行，并对每行做计算或分组。
