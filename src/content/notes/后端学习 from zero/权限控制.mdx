对于单表 CRUD，谁能做、谁不能做，本身就是一个后端问题。

几乎所有接口都要依赖登录状态，因为系统必须知道：

1. 有哪些数据。
2. 这些数据和谁有关。
3. 谁能看、改、删除这些数据。

所以后端系统里，只有登录和注册这类接口通常不需要已有登录态；其他请求都应该在进入业务逻辑前完成身份识别和权限判断。

## 身份认证与权限控制

身份认证回答的是：

```text
你是谁？
```

权限控制回答的是：

```text
你能做什么？
你能操作哪份数据？
```

简单系统里，可以在登录时区分用户身份，比如管理员、员工、普通用户；之后每个请求经过拦截器，从 token 或 session 中解析身份，再决定是否放行。

## 拦截器位置

一个常见请求链路：

```text
request
-> auth interceptor
-> controller
-> service
-> mapper
-> response
```

拦截器适合做通用认证，比如：

1. 检查 token 是否存在。
2. 校验 token 是否有效。
3. 解析当前用户 ID 和角色。
4. 把当前用户信息放进上下文。

更细的业务权限通常不应全塞进拦截器，而是在 service 里结合业务对象判断。比如「用户只能删除自己的评论」就必须查评论归属。
